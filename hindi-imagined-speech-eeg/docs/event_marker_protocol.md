# Event-Marker Protocol

**Status:** Draft. This document expands Section 14 of
`docs/experimental_protocol.md` into a standalone specification, since
the event-marking method is one of the most consequential and most
frequently under-specified parts of an imagined-speech EEG protocol —
it is the single point where "what the participant was doing" gets
tied to "which slice of EEG corresponds to it." Nothing here is final
until it carries an explicit approval note (see
`docs/supervisor_approval_checklist.md`).

## 1. Why This Needs Its Own Document

Epoching (`preprocessing/preprocessing_pipeline.md`, Step 12), the
`cue_onset`/`imagination_onset`/`imagination_offset`/`rest_onset`/
`rest_offset` fields in `metadata/trial_metadata.csv`, and any future
claim about decoding accuracy all depend on markers that are (a)
precisely timed, (b) unambiguous, and (c) generated by a method the
target population could plausibly use. Getting this wrong is not a
preprocessing inconvenience — it silently corrupts every epoch built on
top of it, in a way that may not be visible until analysis fails to
work.

## 2. Two Candidate Marking Methods — Full Comparison

| | Self-initiated (keypress) | Cue-locked (fixed-duration) |
|---|---|---|
| **How it works** | Participant presses a key immediately before speaking/imagining; that keypress event is the marker | Every stage's duration is predetermined by the stimulus-presentation system; markers are emitted on a fixed schedule, not by participant action |
| **Precedent** | Used in Kostulin et al. (2026) and similar work | Used in simpler cued-recall paradigms; less common in the specific papers we reviewed, but standard in many ERP-style cognitive EEG designs |
| **Timing precision** | Depends on reaction time and keypress-registration latency; introduces some jitter | Precisely known in advance; no participant-driven jitter |
| **Motor artifact risk** | Right-hand (or other) keypress can produce a motor-related EEG/EMG artifact overlapping the early post-marker window — documented concern in Kostulin et al. | None from the marker mechanism itself |
| **Compatibility with target population** | Requires reliable, intentional motor action — a real problem for the project's long-term motivation (e.g. ALS, locked-in patients) | Does not require any motor action; compatible with an eventual motor-impaired user |
| **Naturalism** | More self-paced, arguably more naturalistic | Less naturalistic; participant must synchronize to an external schedule rather than their own pace |
| **Current recommendation** | Not recommended as primary method | **Recommended**, pending pilot validation |

**This recommendation is not yet approved.** See
`docs/supervisor_approval_checklist.md`, item on event-marker method.

## 3. Formal Marker Set

(Reproduced from `docs/experimental_protocol.md`, Section 14.1, kept in
sync — if the two ever disagree, this document is the source of truth
for markers specifically.)

| Marker | Meaning | Generated by (cue-locked design) |
|---|---|---|
| `REST_ON` | Inter-trial or baseline rest begins | Stimulus presentation system, on a fixed/jittered timer |
| `CUE_ON` | Stimulus (word/phrase) is presented | Stimulus presentation system, at cue display time |
| `IMAGINE_ON` | Production window begins | Stimulus presentation system, at fixed window start |
| `IMAGINE_OFF` | Production window ends | Stimulus presentation system, at fixed window end |
| `TRIAL_END` | Trial fully completed | Stimulus presentation system |

Rest-only trials (no stimulus) still emit `REST_ON` and `TRIAL_END`,
with `IMAGINE_ON`/`IMAGINE_OFF`/`CUE_ON` omitted or set to `NA` — this
must be handled consistently in both the stimulus-presentation code and
the `trial_metadata.csv` schema (see `docs/data_dictionary.md`).

## 4. Timing Precision Requirements

- Markers must be written to the same data stream/clock as the EEG
  recording (i.e. hardware- or software-synchronized event channel),
  not logged separately by the stimulus-presentation computer on an
  independent clock, to avoid clock-drift misalignment over a session.
- Target marker latency/jitter tolerance: **to be determined** once
  hardware is finalized, but should be measured and reported explicitly
  during piloting (e.g. "marker-to-EEG-sample latency measured at X ms,
  SD Y ms across N test triggers") rather than assumed to be
  negligible.
- Any known fixed latency (e.g. display refresh delay for a text cue)
  should be measured once and either corrected for or explicitly
  documented as an offset in `preprocessing/preprocessing_pipeline.md`.

## 5. Validation Plan for This Protocol

Before this marking method is used in real participant sessions:

1. **Bench test**: verify markers are received by the EEG system with
   the expected count, order, and approximate timing, using the
   stimulus-presentation software alone (no participant).
2. **Protocol pilot** (see `docs/experimental_protocol.md`, Section 24):
   verify markers behave correctly with a real participant going
   through the full trial sequence, including edge cases (early
   session end, participant confusion, technical interruption).
3. Record actual measured latency/jitter from the pilot and update
   Section 4 above with real numbers before finalizing.

## 6. Mapping to `trial_metadata.csv`

| Marker | Corresponding `trial_metadata.csv` field |
|---|---|
| `REST_ON` (pre-trial) | `rest_onset` of the *previous* trial, or a dedicated pre-session baseline field (not yet in schema — flag if needed) |
| `CUE_ON` | `cue_onset` |
| `IMAGINE_ON` | `imagination_onset` |
| `IMAGINE_OFF` | `imagination_offset` |
| `TRIAL_END` → next `REST_ON` | `rest_onset` / `rest_offset` |

This mapping must be implemented identically in whatever script writes
`trial_metadata.csv` from raw event logs — any discrepancy here is a
silent data-quality bug, not a cosmetic one.
